## Two real defects found during commissioning, both fixed

Task 5's own job — proving the O5 system works, not just that its unit tests pass — surfaced two genuine gaps already present in the accepted Task 4 baseline. Neither was introduced this session; both were found because Task 5 required exercising real end-to-end coordinator behavior instead of stopping at REVIEW or at a hand-fabricated event.

### 1. Fallback-routed packets could never reach ACCEPTED (fixed)

**Symptom:** commissioning scenario 1 ("primary provider exhausts, plan-pinned fallback succeeds") could not complete as specified. A packet routed through a genuine plan-pinned fallback always failed review with `ReviewRefused(REVISION_MISMATCH)` and stayed stuck in REVIEW forever.

**Root cause:** `coordinator.py::_assigned_worker_override()` correctly computes the fallback route's provider/model for invocation, but this override was never persisted back to the durable enrolled-packet artifact. `review.py::_decide()` re-loads that artifact via `_load_enrolled_packet()`, which always reflects the packet's static, pre-plan `assigned_worker` default. `replay.py::_cross_object_replay_checks` compares the actual worker result's identity against that stale value — always disagreeing for a genuine fallback.

**Fix (comparison-side, not artifact mutation):** `validate_replay_bundle` gained an optional `trusted_attempt_worker` parameter — the ATTEMPT_STARTED-recorded worker identity for the specific attempt under review, already correct and already durable, supplied alongside the bundle exactly like the pre-existing `trusted_dependency_provenance`/`trusted_reviewer_sessions` parameters. When present, it is ground truth; when absent (every pre-existing caller), behavior is byte-identical to before. `review.py::_decide()` and `coordinator.py::_accepted_replay_evidence()` (the symmetric dependent-promotion re-validation path, same latent bug, found and fixed in the same pass) both now supply it.

The enrolled packet artifact was deliberately **not** mutated — doing so would break its own `packet_sha256` self-hash check (`harness_contracts/v1/packet.py::validate_packet`) and the terminal-seal binding check (`seals_runtime.py::_upstream_digests`), both of which depend on the artifact staying byte-identical to what was hashed at enrollment.

**Verification:** the non-fallback mismatch-rejection property (the real security check this touches) was independently confirmed unweakened — `TestPacketAuthority`/`TestReplayCrossObject` (6 tests specifically covering worker/lane/provider/model mismatch rejection, 20 tests total in that selection) all still pass, none of which supply `trusted_attempt_worker`.

### 2. Legacy lane-based reassignment is unconstrained by plan-pinned routing (detection backstop added, live prevention deliberately deferred)

**Finding:** `classify_runtime.py`'s O3-era Kimi→Sonnet lane reassignment (`resolve_open_attempts`/`_resolve_reassignment_cause`) runs unconditionally in `coordinator.py`, with no `plan` parameter threaded through it at all. Neither the execution-plan schema nor `enroll.py`'s plan-membership check constrains a packet's `lane`/`sonnet_reassignment_allowed` against the plan's own `routes` table. A plan-governed packet can, today, still be auto-reassigned by the legacy mechanism to a target the bound plan never authorized for its capability class.

**Decision (Alex, this session):** fix scope was explicitly bounded to a **reconciliation-only detection backstop**, not live prevention. `reconcile.py`'s tamper-detection now fails closed (`all_invariants_passed = False`) when a packet's folded state shows a legacy-lane reassignment (`from_lane: "kimi_implementation"` → `to_lane: "sonnet_implementation"`) whose ACTUAL invoked `(provider, model_id)` — read from the packet's own durable `ATTEMPT_STARTED` event under the `sonnet_implementation` lane via `_o5_reassignment_target_identity`, never assumed or hardcoded — does not exactly match a hop the packet's plan-pinned route table for its capability class actually lists. **Corrected in a follow-up revision pass** (an independent adversarial review found the original implementation checked only whether the route table mentioned the `anthropic` provider ANYWHERE, so a reassignment to any anthropic model — including one the plan never authorized — would sail through undetected whenever the route table happened to name a different anthropic model for a legitimate purpose; proven provably inert under the O5 test suite's own canonical multi-hop route table, `test_o5_budget_runtime.py`'s `_default_routes()`, which already lists `anthropic/claude-sonnet-4-5`). The check is now target-granular, not provider-granular: a route table that authorizes `anthropic/claude-sonnet-4-5` does not thereby authorize every anthropic model, only that one. If the real invoked target cannot be determined with full confidence from durable evidence, the check fails CLOSED (flags the packet) rather than fails open. Implemented as an extension of the plan doc's own `route_not_in_plan` tamper case, verified by `test_reconciliation_fails_closed_on_o5_tamper[route_not_in_plan]` (the original fixture, corrected to use a real anthropic target so it still exercises the right thing under the new check) and by the new `test_reconciliation_fails_closed_on_o5_tamper[route_not_in_plan_realistic_route_table]`, which proves the check fires under a route table that already contains a real anthropic hop for a different model — the exact shape the original check could not have caught.

**What this does and does not do, stated plainly:** this detects the disagreement after the fact, in reconciliation. It does **not** prevent the live invocation from happening — a real, ungoverned model call under this scenario would still occur before reconciliation ever runs. Fixing `classify_runtime.py`/`enroll.py` to prevent it live is out of scope for Task 5 (those files were never in Task 5's declared file list) and is recorded here as an explicit residual, matching the audit doc's own required "every non-action" section below — not silently dropped, not silently expanded into.

### 3. `_o5_disposition` classified a stale pause over a live re-claimed attempt (fixed)

**Symptom:** a packet that was genuinely backoff-paused (a real, non-indefinite `next_eligible_at` window recorded on a `PACKET_PAUSED` event) and then successfully re-claimed — reaching RUNNING or REVIEW with a real attempt in progress — still reported `disposition == "paused_provider"` in the reconciliation report, with `all_invariants_passed` reporting `True` even though the packet's true, live status was being hidden rather than surfaced.

**Root cause:** `reconcile.py::_o5_disposition` checked `_o5_packet_paused_events()` BEFORE checking whether the packet's fold state was RUNNING/REVIEW. `recovery.py`'s `PACKET_PAUSED` fold branch is schema-forbidden from transitioning packet state, and its `next_eligible_at` uses a real backoff window verbatim when one is supplied (not always the indefinite sentinel — only a pause with no natural expiry gets that) — so a packet that was backoff-paused and later successfully re-claimed still carried its OLD `PACKET_PAUSED` event in the journal even though it had since been claimed, and the classifier read that stale event ahead of the live claim.

**Fix:** `_o5_disposition`'s check order is now: (1) terminal/resting fold states (ACCEPTED/QUARANTINED/HUMAN_REQUIRED/REVISE, unchanged); (2) RUNNING/REVIEW — a live or completed-but-unresolved attempt in flight — returns `None` (indeterminate) regardless of any earlier `PACKET_PAUSED` record; (3) any other non-terminal state with `attempts_started > 0` (e.g. READY after an infra retry) is likewise indeterminate, checked before the pause-event lookup so a stale pause from before that packet was ever claimed can never outrank the fact that it has been; and only then (4) a packet that has never been claimed at all falls through to pause-event classification (`paused_provider`/`blocked_human`).

**Verification:** the new `test_backoff_paused_then_reclaimed_packet_is_indeterminate_not_paused` constructs two packets, each backoff-paused with a real `next_eligible_at` window and then successfully re-claimed — one carried to REVIEW, one left RUNNING — and asserts `disposition is None` (not `"paused_provider"`) for both, with `all_invariants_passed is False` and a `plan_disposition_indeterminate` attention item present for each. The pre-existing terminal-partition identity test and all nine original tamper cases continue to pass unchanged.

### 4. The plan-route check covered only legacy-reassignment-tagged attempts, not every unauthorized attempt identity (fixed)

**Symptom:** the route-authorization check added for defect #2 was gated behind `if pkt.get("reassignment_used") and pkt.get("lane") == "sonnet_implementation":`. A plan-member packet whose durable `ATTEMPT_STARTED` recorded a `(provider, model_id)` the bound plan's route table for that capability class never lists — but which did NOT go through the legacy Kimi-to-Sonnet reassignment path — produced zero violations. Reviewer's live probe against exactly this shape: `codes=set() invariants=True`, with a real `ATTEMPT_STARTED` recording `anthropic`/`claude-opus-9`, a model absent from the route table entirely.

**Why this mattered more after defect #1's fix:** `replay.py::_cross_object_replay_checks` now prefers the `ATTEMPT_STARTED`-recorded `trusted_attempt_worker` identity over the packet's enrolled `assigned_worker` default when validating a review (correct and necessary for legitimate plan-pinned fallbacks) — so review no longer refuses an attempt merely because its identity diverges from the packet's enrolled default. The compensating control ("...and that identity must actually be a plan-authorized hop") existed only for the narrow legacy-reassignment sub-case, leaving every other way an attempt's recorded identity could diverge from what the plan authorizes unchecked by reconciliation too.

**Fix:** the check now runs for EVERY plan-member packet, over EVERY `ATTEMPT_STARTED` entry already present in that packet's `row["route_history"]` (no longer only the ones recorded under the `sonnet_implementation` lane) — reusing `_o5_route_history`'s existing output directly rather than a second, narrower re-derivation. The dedicated `_o5_reassignment_target_identity` helper (which correlated `ATTEMPT_STARTED` events against the `sonnet_implementation` lane specifically) is removed as redundant: a legacy reassignment's invoked identity is itself just one more `ATTEMPT_STARTED` entry, so the general check subsumes it without a separate code path. The violation code is renamed `attempt_route_not_in_plan` (from `reassignment_route_not_in_plan`) to honestly describe what it now checks.

**Verification:** new tamper case `attempt_route_not_in_plan_no_reassignment` reproduces the reviewer's probe shape exactly (`ATTEMPT_STARTED` recording `anthropic`/`claude-opus-9`, no `sonnet_reassignment_allowed`, no `provider_exhausted_reassignment` cause anywhere in the journal) and asserts `all_invariants_passed is False`.

### 5. The authorization predicate ignored `enabled`/`qualification_id` (fixed)

**Symptom:** the authorization predicate matched only `(hop["provider"], hop["model_id"])`, while the live route selector (`budget_runtime.py::select_capable_route`) additionally requires `hop.get("enabled") is True` and a present, valid-shaped `qualification_id` (`is_harness_id`) before treating a hop as usable. A hop the plan lists but explicitly disables, or lists without a valid qualification, read as "authorized" by reconciliation even though the live coordinator would never actually route there.

**Fix:** the new `_o5_hop_authorized(routes, identity)` helper requires `enabled is True` and `is_harness_id(qualification_id)` on the matched hop, in addition to the exact `(provider, model_id)` match — mirroring `select_capable_route`'s own real eligibility gate condition-for-condition, not an approximation of it. **Corrected in the third review-fix pass (defect #8 below):** this claim was true for the enabled/qualification_id conditions specifically, but was found to still be an approximation overall — it checked the raw declared route list, not the live selector's actual `fallback_to` reachability chain. **Verification:** new tamper case `attempt_route_disabled_hop` publishes a plan whose route table lists a hop with the attempt's exact invoked `(provider, model_id)` but `enabled: False`, and asserts `all_invariants_passed is False`.

**Regression check for both:** the existing positive control (renamed `test_attempt_route_not_in_plan_is_target_granular_not_provider_granular`, formerly `test_reassignment_route_not_in_plan_is_target_granular_not_provider_granular`) still asserts a legitimately plan-authorized, enabled, validly-qualified identity does NOT trip `attempt_route_not_in_plan`; the pre-existing `route_not_in_plan`/`route_not_in_plan_realistic_route_table` tamper cases (both legacy-reassignment shapes) still fail closed under the generalized check, since a legacy reassignment's invoked identity is just one more entry the general check now reads; and `test_o5_commissioning.py`'s full 15-test suite (untouched, not authorized for edits) continues to pass unmodified. **Scope correction (third review-fix pass):** the accurate claim this evidence supports is narrower than originally stated — no false positive WITHIN a single plan-bound run, which is what these 15 single-run commissioning tests and the single-run tamper/positive-control fixtures can actually demonstrate. ### 7. Route authorization was checked against the CURRENT run's plan, not each attempt's OWN run's plan (fixed)

**Symptom:** `_o5_route_history`/the authorization check in `_o5_plan_extension` filtered journal events by `packet_id` only, never by which `run_id` a given `ATTEMPT_STARTED` actually happened under, and checked every one of a packet's attempts — regardless of which run produced them — against `plan`, the single plan resolved for whichever run the CALLER is currently reconciling. Plan authorization is inherently run-scoped (`bound_execution_plan_for_run` selects the bound plan by `run_id`, and a state root can legitimately see several runs, each with a different bound plan — a plan amendment mid-project is a real, supported pattern; `test_o3_p5_resume.py` already exercises multiple runs against one state root). The reviewer proved this live with a two-run state root: run-1 bound a plan authorizing a `kimi` identity; run-2 bound an amended plan that no longer authorized it. A packet's attempt that genuinely ran under run-1, on `kimi`, fully legitimate under run-1's OWN bound plan, was reported as `attempt_route_not_in_plan` when reconciling run-2 — a false positive. Symmetrically, an attempt genuinely unauthorized under run-2's own plan was missed when reconciling run-1, since it was (wrongly) checked against run-1's plan instead — a false negative.

**Fix:** each `ATTEMPT_STARTED` entry is now checked against the plan that was ACTUALLY BOUND for THAT specific event's own `run_id`, not against the plan bound for the run currently being reconciled. `_o5_route_history` now also captures each entry's own `run_id` internally (stripped back off before the entry is written to the report's public, schema-closed `route_history` field — the schema's `additionalProperties: false` on that field is unchanged and still enforced; the extra `run_id` never reaches the served report). A new helper, `_o5_plan_for_run(state_root, journal_events, for_run_id, cache)`, resolves and memoizes the authenticated plan bound for an arbitrary `run_id`, called once per distinct run_id encountered across a packet's route history (cached across the whole `_o5_plan_extension` call, pre-seeded with the current run's own already-resolved plan to avoid re-authenticating it). `capability_class` for each entry's authorization check is also re-derived from THAT run's own plan-packet row, not the current run's, since a plan amendment can change a packet's capability_class assignment along with its routes. The dedup key that avoids re-checking the same identity twice changed from `identity` alone to `(identity, run_id)` — the same `(provider, model_id)` invoked under two different runs can be authorized under one and not the other, so collapsing across runs could hide a real violation. If an attempt's own run's plan cannot be authenticated or was never bound, the check fails CLOSED (a new `attempt_route_plan_unresolvable` code) rather than skipping that attempt.

**`bound_execution_plan_for_run`/`recovery.py` — nothing unexpected found:** its behavior is exactly what the fix needed — it filters `EXECUTION_PLAN_BOUND` events by exact `run_id` match (last-write-wins if a run somehow re-binds), returns `None` for an unbound run rather than raising, and raises `IntegrityError` only for a genuine authentication failure (corrupted/tampered artifact) — all three outcomes were already handled correctly by the existing single-run call at the top of `_o5_plan_extension`, so the new per-entry helper only needed to add memoization and route `IntegrityError` into a fail-closed report finding instead of letting it propagate. `_fold_journal` (also `recovery.py`) confirms packet enrollment/state accumulates across the WHOLE journal regardless of `run_id` (it takes no `run_id` parameter at all) — this is what makes a packet enrolled under one run still appear, and still get its route history checked, when a DIFFERENT run is reconciled; understanding this was necessary to design a fixture that actually exercises the false-positive and false-negative directions rather than being short-circuited by an unrelated `packet_outside_bound_plan` finding.

**Verification:** new test `test_route_authorization_is_scoped_to_each_attempts_own_run_not_the_reconciled_run` builds a two-run, two-plan, two-packet state root (`pkt-a` enrolled/attempted only under run-1 on an identity Plan A authorizes and Plan B does not; `pkt-b` enrolled/attempted only under run-2 on the SAME identity, which Plan B does not authorize either — both packets members of BOTH plans, a genuine amendment, not a removal) and asserts: `pkt-a` is never flagged in EITHER run's report (the false-positive fix, direct proof it doesn't bleed into run-2's report); `pkt-b` IS correctly flagged in BOTH run's reports (the false-negative fix, direct proof reconciling run-1 doesn't miss a violation that happened under run-2's own plan); and the violation's own detail text names the correct run and identity. Verified RED against the pre-fix code (reintroducing the single-cache-lookup shape reproduced the exact false positive the reviewer described) before confirming GREEN against the fix.

### 8. The route-authorization check ignored the live selector's `fallback_to` reachability chain (fixed)

**Verification:** new tamper case `attempt_route_unreachable_via_fallback_chain` (added to the matrix, now 13 cases — see "Tamper matrix" below) reproduces the reviewer's exact three-hop table and asserts `all_invariants_passed is False`. ### 9. The plan-level attempt-budget check compared a packet's CUMULATIVE attempts_started against the CURRENTLY-RECONCILED run's plan, not each attempt's own run's plan (fixed)

**Symptom:** the `plan_attempt_budget_exceeded` check (originally added in the initial build, unchanged by defects #1–#8) compared `pkt.get("attempts_started", 0)` — a single counter folded across the WHOLE journal, never reset or scoped per run (`recovery.py`'s fold has no `run_id` parameter at all) — against `attempt_limit` read from `plan_packet`, which came from `plan`, the ONE plan resolved for whichever run the caller is currently reconciling. The reviewer proved it live: a packet ran 2 attempts under run-1, whose bound plan (Plan A) allowed 3 — fully legitimate, and reconciling run-1 correctly showed `all_invariants_passed: True`. **Investigation (which model is actually correct, not assumed):** the task instruction required determining whether attempt-budget checking is genuinely meant to be run-scoped (mirroring D2) or cumulative-across-runs-against-one-governing-plan by design, and documenting whichever is correct rather than silently picking one. Read `budget_runtime.evaluate_preclaim` (the live gate) and its `_journal_usage` helper directly: `attempts_started` there is ALSO a single journal-wide counter with no `run_id` scoping at all (confirmed by reading `_journal_usage`'s signature and body — it takes `packet_id`, not `run_id`) — but it is compared, at live decision time, against exactly ONE plan: whichever plan is bound to the coordinator run that is CURRENTLY LIVE and about to grant (or refuse) a NEW claim. The live gate never re-judges an attempt that ALREADY happened against a plan adopted afterward — a plan amendment that tightens `attempt_limit` correctly stops FURTHER claims (that is `evaluate_preclaim`'s own job, confirmed by reading its `used >= limit + slack` check), but nothing in the live coordinator path ever revisits a past, already-granted claim's legitimacy once a later plan changes the number. This settles the question: run-scoping is correct, not the cumulative alternative — a reconciliation report that retroactively brands an attempt a "budget VIOLATION" because a later, unrelated plan amendment tightened the limit does not match what the live system itself does, and would fail a run's own report for a plan amendment that run had no part in. ### 11. The reviewer-identity implementer set (defect #10) was computed over the WHOLE journal instead of scoped to events preceding each claim — a retroactivity bug (fixed)

**Symptom:** `_o5_plan_extension` computed `implementer_identities = _implementer_invocations(journal_events)` ONCE, over the entire journal, and reused this single whole-journal set when checking EVERY attempt's authorization via `_o5_hop_authorized`. ### 12. The route-authorization dedup key did not account for the seq-dependent implementer set defect #11 introduced — a fail-open regression (fixed)

**Symptom:** the route-authorization loop dedups `ATTEMPT_STARTED` entries on `(identity, run_id)` — correct through defect #11, when `_o5_hop_authorized`'s verdict for a given entry was a pure function of (plan-for-that-run, capability_class, identity). Defect #11's fix made the verdict ALSO depend on the attempt's own `seq`, via a per-attempt-scoped implementer set (`_o5_implementers_before_seq`) that only grows as `seq` advances — but the dedup key was never extended to match. Since iteration is in seq order and the scoped set only grows, the SURVIVING (earliest-seen, by dedup) attempt on any given `(identity, run_id)` is, by construction, the MOST PERMISSIVE one — so a genuinely later, actually-illegitimate attempt on that same identity (e.g. a review-class packet's second attempt on an identity that became an "implementer" identity between the first and second attempt) is silently skipped by dedup: never checked, never flagged. **This is more serious than defect #11 itself, not merely another instance of it:** defect #11 was a false POSITIVE (a legitimate attempt could be wrongly flagged); this is a false NEGATIVE (a genuinely illegitimate attempt reads as clean) — the direction this module's stated convention is fail-closed everywhere against (`attempt_route_plan_unresolvable` on an unauthenticated plan or an unresolvable plan-member row, the `before_seq is None` full-set fallback in `_o5_implementers_before_seq` itself, and every one of the 13 tamper cases). The reviewer reproduced this live, through the real `build_reconciliation_report`: an `adversarial_audit` packet's attempt 1 on `openai/gpt-5.6-terra` (legitimate, no implementer yet), a different packet then implements on that same identity, then the audit packet's attempt 2 on the SAME identity — exactly the self-review the live gate would refuse — produced `codes: set()`, `all_invariants_passed: True`. A control case (only the post-implementer attempt exists, no earlier legitimate one to collide with in dedup) correctly got flagged, confirming the miss was specifically caused by the dedup collision, not a broader break in the underlying check — this control case is `test_review_capability_class_excludes_hop_matching_recorded_implementer_identity` (defect #10's own test, already in the suite, unaffected by either defect #11 or this fix).

**Why defect #11 didn't catch this:** defect #11's own fix correctly scoped WHAT `_o5_hop_authorized` is judged against but did not separately ask whether the loop's pre-existing dedup mechanism — added for an earlier defect (#7/D2), back when the per-entry verdict depended only on `(identity, run_id)` — still safely deduplicated entries once the verdict also depended on `seq`. It no longer did: two `ATTEMPT_STARTED` entries can share `(identity, run_id)` and legitimately produce different verdicts once seq-scoping is in play, and the loop kept collapsing them to one, silently discarding the later one without ever evaluating it.

**Fix (matches the reviewer's own candidate fix):** the scoped implementer-set computation (`_o5_implementers_before_seq(implementer_invocations_by_seq, entry.get("seq"))`) now runs BEFORE the dedup check for each entry, not after, and the dedup key is extended from `(identity, run_id)` to `(identity, run_id, identity in entry_implementer_identities)` — whether THIS specific attempt's own identity is, at this attempt's own seq, in its own scoped implementer set. This restores the exact guarantee dedup originally relied on: any two entries sharing the (now three-part) key are provably guaranteed to produce the identical `_o5_hop_authorized` verdict, because that function's reviewer-diversity exclusion only ever checks exact membership of the attempt's own identity in the passed set (see its own docstring: a caller passing `implementer_identities` gets a hop that matches ONE OF THEM treated as unauthorized — membership, not the set's other contents) — so the boolean fully captures the set's only effect on this identity's own authorization, and keying on it (rather than the raw seq, or the whole set) is sufficient, not merely convenient. The pre-existing run-scoping comment immediately above this loop (added by defect #7/D2, explaining why `(identity, run_id)` and not `identity` alone) is extended in place, not left describing only half of what the key now does, to also explain this third component and the specific fail-open shape it closes.

**Verification:** new test `test_second_attempt_on_same_identity_after_intervening_implementer_is_flagged_despite_dedup` reproduces the reviewer's exact scenario: a review-capability-class packet (`pkt-review`, `independent_review`) makes a first, legitimate `ATTEMPT_STARTED` on identity X (no implementer yet), goes to REVISE, is requeued; a DIFFERENT packet (`pkt-impl`) then implements on that SAME identity X; `pkt-review` then makes a second `ATTEMPT_STARTED`, still on X, still within the same run — asserted to be the ONLY `attempt_route_not_in_plan` violation for `pkt-review` (not zero, and not two — the fix must neither under- nor over-correct: not flag the earlier, legitimately-authorized first attempt, and not stop deduping genuinely-identical repeats), with `all_invariants_passed is False` on both fields, asserted equal.
