# Position Paper registry generalization — baptism migrated, tongues added — 2026-07-31

**Plain-English summary:** The one-off baptism build from yesterday is now a real, reusable system — the matching, serving, and bypass logic is shared code driven by a small list of registered topics, not custom code per topic. Baptism was migrated onto it with its original behavior provably intact, and speaking-in-tongues was added as the second topic, proven end-to-end the same rigorous way baptism was. Along the way, testing the two topics against each other (something that couldn't be tested with only one topic) found two real bugs — one of which, a false match on generic "spiritual gifts" and "prophecy" questions, was already live in yesterday's shipped baptism code and had simply never been caught — and both were fixed and re-verified before this was called done. Adding a third future topic is genuinely just "write the document, add a few lines of config" for the code-wiring itself, but whether that new topic's wording stays cleanly distinct from the two already registered can only be found out by actually testing it once written — that part is never guaranteed in advance, and this session proved that firsthand. Nothing has been committed — the code is built, tested against real API calls, reviewed, and approved, and is waiting on Alex's decision on how to stage the commit(s).

## What changed

**`backend/app/services/position_papers.py`** — rewritten from a single-topic module into a registry-driven one. 528 lines (was 333). A `PILLARS` list holds one entry per registered topic (baptism, tongues), each with: which document to load, the topic's "positive" reference phrases, one or more "contrast" reference phrases for topics it must NOT be confused with, its own matching threshold, and its own voice-prompt framing. One shared matcher, one shared content loader, one shared answer-voice template read this list — there is no per-topic branch anywhere in the file (confirmed by direct code inspection, not just by the build report).

**`backend/app/routers/chat.py`** — the existing interception point (added yesterday) now passes which topic matched through to the shared generator, instead of always generating baptism's answer. 20-line diff, otherwise unchanged from yesterday.

## How matching now works, in plain terms

Every registered topic has a handful of reference phrases describing what it IS (e.g. baptism's title + a short description) and a handful describing what it is NOT — topics close enough in wording or theme to cause real confusion (baptism's: water baptism, general spiritual gifts, the gift of prophecy; tongues': general spiritual gifts, prophecy, and the tithing/teacher-citation class of question). An incoming question only matches a topic if it's similar enough to that topic's own reference phrases AND more similar to those than to any of its contrast phrases. When two topics both look like a real answer to the same question, a tie-break rule (Alex's decision below) decides which one serves the answer.

## Two decisions made this session (both brought to Alex, not decided silently)

1. **A genuine two-topic tie.** One of baptism's own original test questions — "How do I receive the baptism of the Holy Spirit and speak in tongues?" — scored an almost-exact tie between baptism and tongues once both were registered (a razor-thin 0.0089 gap, versus a healthy 0.07+ gap on every other borderline case tested). This is a real double-topic question, not a bug. **Alex's decision: baptism wins ties** — the tongues paper itself frames tongues as "one expression of" Spirit baptism, so baptism is the broader topic. Implemented as an explicit, justified rule (not an arbitrary pick), and re-verified: that exact question now correctly routes to baptism, while a different, more clearly tongues-leaning double-topic question still correctly goes to tongues.

2. **A real accuracy bug, found by finally testing the two topics against each other.** Generic questions like "What are the nine gifts of the Spirit?" and "How does the gift of prophecy work in a church service?" were incorrectly getting served the baptism answer, because baptism's only "not this" reference phrase was about water baptism — nothing distinguished it from ordinary spiritual-gifts or prophecy questions. **This exact bug was already live in yesterday's shipped baptism code** — it just had no second topic around to expose it until this session. A smaller, fresh version of the same class of bug also turned up for tongues (one teacher-citation-style tithing question scored just inside its threshold). **Alex's decision: fix both now.** Baptism gained two more "not this" reference phrases (general spiritual gifts, prophecy); tongues' threshold was tightened slightly. Every previously-correct case was re-checked and still passes; every broken case is now fixed.

## One thing disclosed, not hidden: a thinner safety margin as the cost of the fix above

Fixing the gifts/prophecy false-match came at a real cost for one baptism test question ("How can I be filled with God's power for ministry?") — because baptism's own paper genuinely does talk about spiritual gifts as one effect of Spirit-baptism, sharpening the boundary against gifts-questions also thinned this question's own safety margin, from a comfortable +0.166 down to a real but thin +0.011. It still correctly matches baptism. If a similar question ever phrased slightly differently dipped just below that margin, the failure mode is safe, not wrong — it would simply get a normal, cited answer instead of the house-voice one, never a fabricated or misattributed answer. **Alex's decision: ship as-is** rather than spend more of this session trying to claw back that margin, since doing so risks reopening the bug just fixed.

- **Proof the right topic's content and voice actually get used**, not just "an answer came back": the real API call sent to the AI was captured and inspected for both topics, confirming baptism's answer uses baptism's content/voice and tongues' answer uses tongues' content/voice, with no bleed-through in either direction — including confirming a shared template can't accidentally tell one topic's answer to avoid a heading that belongs to a different topic.
- **A hypothetical third topic was actually added and removed as a test**, using an already-ingested real document. Adding it required exactly 9 lines, entirely inside the registry list — no new code. It was then fully run end-to-end (matched, loaded, answered for real) before being cleanly reverted, with the registry confirmed back to exactly its original two-topic state afterward.

## Is adding a third pillar now pure content work? Answered precisely, not oversold

**Half yes, half "it depends, and you won't know until you try":**
- **The wiring itself: yes, provably.** The 9-line, zero-new-code test above proves that *registering* any already-ingested document as a new topic is pure configuration.
- **Whether that topic will actually stay cleanly distinct from the others: no, not guaranteed in advance, for anyone.** This is not a hedge — it's exactly what happened in this session. Baptism's original calibration looked completely clean when it was the only topic, and had a real, live confusion bug for a full day before speaking-in-tongues came along and exposed it. Any third topic will need its own real calibration pass (its own reference phrases, its own "not this" list, tested against the topics already registered, not just against its own hand-picked test questions) before going live — that's a short, bounded task, but it is a task, not zero work.

## Technical detail for reference

- **Session type:** Repo-only multi-step build (CLAUDE.md Session Routing) — harness path, `executor`/`planner-reviewer` two-agent loop, continuing the same feature from yesterday's committed work (`256cdce`, `b20453d`). Zero database writes for the entire session — every DB interaction was a read-only `SELECT` (grep-confirmed no `.insert()`/`.update()`/`.delete()`/`.upsert()` anywhere in the touched files); all functional testing called the matching/generation functions directly, never the live metered `/chat` endpoint (whose usage-counting RPCs and conversation-save are real writes).
- **Registry entry shape (`PILLARS`, `position_papers.py`):** `pillar_key`, `document_id` (chunks-table source, read live per request-cycle-cached, same production-safe pattern as baptism's earlier fix), `positive_anchors` (list), `contrast_anchors` (list, per-pillar — baptism: 3 as of this session (water baptism, general spiritual gifts, prophecy); tongues: 3 (general spiritual gifts, prophecy, a teacher-citation-style contrast folded into its threshold rather than a dedicated anchor)), `match_threshold` (per-pillar float; baptism 0.3262 unchanged, tongues 0.3631 raised this session from a calibrated 0.2989), `voice_topic_name`. Headings-to-avoid in the voice prompt are derived dynamically per pillar from that pillar's own loaded content, not a hardcoded list — chosen specifically so a shared template structurally cannot leak one pillar's headings into another's prompt.
- **Tie-break rule:** `TIE_BREAK_EPSILON = 0.02`, empirically justified — sits more than 2x above the real near-tie margin found (BP8, 0.0089) and more than 3x below the smallest real clear-win margin found (X1, 0.0702). Among pillars that individually qualify (clear threshold and beat their own contrasts), the highest-scoring pillar wins UNLESS the top two are within epsilon of each other, in which case baptism wins by explicit priority — never by list/dict iteration order.
- **N+1 discipline, proven not asserted:** an instrumented call-counter across 5 sequential match calls showed exactly 9 embedding calls on the first (8 anchors across both pillars + 1 question) and exactly 1 on every call after (question only) — anchors and bodies are cached once per pillar per process.
- **Baptism migration verification:** `MATCH_THRESHOLD` and both positive anchors confirmed byte-identical to the pre-migration committed constants. The original 15-item test matrix (8 positives, 7 negatives) reproduced to within 0.0001 on 2 of 15 items (embedding-API float noise, not a data change — verified by checking the anchor strings themselves were untouched). The assembled baptism system prompt is NOT byte-identical to the committed version — one line differs (the heading-avoidance list now enumerates baptism's real headings dynamically instead of 2 hardcoded examples), a necessary superset for generalization, not a behavior change in kind.
- **Cross-pillar regression bug found and fixed:** testing each pillar's own negative set against the OTHER pillar (a check that had no reason to exist before a second pillar existed) found baptism's single water-baptism contrast anchor did not exclude general-spiritual-gifts/prophecy questions (4 specific questions misrouted, contrast similarity 0.23–0.26 vs. positive similarity 0.37–0.44). Confirmed via byte-identical per-pillar scoring that this exact false-match already existed in the currently-committed single-pillar system (`256cdce`) — not introduced by this session's migration. Fixed by adding 2 new contrast anchors to baptism (all 4 previously-misrouted questions now score 0.51–0.75 against the widened contrast set, well above their 0.37–0.44 positive similarity). A second, smaller gap (one baptism teacher-citation negative about tithing scoring 0.3155, just inside tongues' original 0.2989 threshold) was fixed by raising tongues' threshold to 0.3631.
- **Cost of the fix on baptism's own positives:** re-verified all 8 original baptism positives against the widened 3-contrast set — all still match, but P1 ("How can I be filled with God's power for ministry?") margin thinned from +0.1659 to +0.0113 (real, ~100x above the observed embedding float-noise floor of ~0.0001, so not at risk of flipping on API noise alone — a genuine coverage/precision tradeoff, not a fragile number).
